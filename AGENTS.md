# AGENTS.md

## 1. Назначение проекта

Этот репозиторий — решение тестового задания на позицию **Quant Researcher / Quant Developer**.

Краткая суть задания:

- предложить понятную стратегию **market making**;
- реализовать backtest-симулятор;
- протестировать стратегию на исторических данных за 3 календарных дня;
- смоделировать выставление и отмену ордеров, fills, inventory и PnL;
- посчитать основные метрики;
- кратко и честно проанализировать результаты и ограничения модели.

Исходные материалы:

- `./TASK-ru.md` — краткое исходное задание;
- `./TASK-en.md` — более полная версия задания на английском;
- `./data/` — исходные данные: order book, trades, funding.

Перед существенными изменениями логики сначала перечитать `README.md`, `TASK.md` и актуальный `RESEARCH.md`.

## 2. Главный принцип: это тестовое, а не production-система

Нужно показать:

- понимание market making;
- умение работать с рыночными данными;
- умение формулировать гипотезы;
- реалистичную модель исполнения;
- корректный учет inventory и PnL;
- понимание ограничений backtest;
- способность делать выводы по результатам.

Не нужно:

- строить production-ready торговую платформу;
- добавлять лишние абстракции;
- делать сложную инфраструктуру;
- проектировать микросервисы;
- добавлять Spring;
- писать универсальный trading framework;
- преждевременно оптимизировать производительность;
- усложнять математику без практической необходимости.

Если есть выбор между более сложным и более простым прозрачным решением, предпочитать простое, если оно корректно проверяет гипотезу.

При этом принципиально важные части должны быть выделены явно:

- стратегия котирования;
- управление inventory;
- использование funding;
- модель ордеров;
- модель fills;
- комиссии;
- latency, если используется;
- расчет PnL;
- риск-лимиты;
- метрики.

Критические настройки не зашивать глубоко в код. Выносить их в конфигурацию, аргументы запуска или один хорошо видимый класс параметров.

## 4. Основной технологический стек

### Java

Основная логика должна быть написана на Java:

- market making strategy;
- backtest engine;
- обработка событий;
- модель ордеров;
- fills;
- inventory;
- PnL;
- risk logic;
- metrics.

Предпочтительно Java 21.

Spring не использовать.

Программа должна запускаться максимально просто из командной строки.

На входе: файлы из `./data` и параметры стратегии/backtest.

На выходе: консольный отчет, CSV и при необходимости другие простые файлы с результатами.

### Python

Python допустим для небольших вспомогательных задач:

- первичный анализ данных;
- проверка качества данных;
- построение графиков;
- подготовка простых отчетов;
- разовые исследовательские утилиты.

Python-скрипты должны быть:

- короткими;
- максимально простыми;
- без сложной архитектуры;
- с понятными названиями;
- с комментариями на русском;
- запускаемыми простой командой:

```bash
python script_name.py
```

Если скрипту нужны параметры, по умолчанию хранить их в начале файла:

```python
# Что анализируем. Для другого дня поменять значение здесь.
DATE = "2026-03-19"
```

Не добавлять argparse, конфигурационные фреймворки и сложную CLI-инфраструктуру без реальной необходимости.

## 5. Требования к Java-коду

Java-код должен быть максимально читаемым для человека, который хорошо знает Python, но может плохо знать Java.

Использовать:

- простые классы;
- простые методы;
- обычные циклы;
- понятные `if`;
- понятные коллекции;
- явные промежуточные переменные;
- очевидный порядок выполнения.

Избегать без необходимости:

- Stream API;
- сложных generic-конструкций;
- функционального стиля;
- reflection;
- dependency injection;
- сложных паттернов ради паттернов;
- глубокой иерархии интерфейсов;
- метапрограммирования;
- чрезмерного использования продвинутых Java features, если они ухудшают читаемость;
- скрытой магии библиотек.

Если обычный `for` понятнее stream — использовать `for`.

Если два явных метода понятнее универсальной generic-абстракции — использовать два метода.

### Комментарии

Каждый метод, содержащий бизнес-логику, должен иметь короткий комментарий на русском:

- что делает;
- зачем нужен;
- какие важные допущения использует.

Каждый нетривиальный логический блок внутри метода также кратко комментировать.

Не комментировать очевидный синтаксис.

Плохо:

```java
// Увеличиваем i
i++;
```

Хорошо:

```java
// Учитываем только sell-aggressor сделки: именно они могут исполнить наш bid.
if (!trade.isMakerAsk()) {
    ...
}
```

## 6. Две роли Codex

Codex должен явно различать две роли.

### Роль A. Quant Researcher / планировщик исследования

Главный рабочий документ этой роли — `./RESEARCH.md`.

Это **живой документ и источник истины** по исследованию.

В этой роли Codex:

- анализирует исходные данные;
- помогает формулировать вопросы к данным;
- формулирует гипотезы;
- фиксирует допущения;
- проектирует стратегию;
- проектирует backtest на уровне смысла;
- определяет необходимые метрики;
- отмечает риски неправильной симуляции;
- фиксирует, что уже проверено;
- формулирует следующий конкретный шаг.

Важно: не перепрыгивать сразу в реализацию, если исследовательское решение еще не принято.

Перед крупным изменением стратегии:
1. сначала обновить `RESEARCH.md`;
2. затем менять код.

Если исследование опровергло гипотезу:
- не скрывать это;
- пометить гипотезу как отвергнутую;
- кратко написать почему;
- зафиксировать новое решение.

Codex не должен «доказывать», что стратегия прибыльна. Задача — честно проверить гипотезу.

### Роль B. Архитектор / разработчик

В этой роли Codex:

- читает актуальный `RESEARCH.md`;
- реализует только уже принятые исследовательские решения;
- проектирует минимально достаточную архитектуру;
- пишет Java-код;
- пишет простые Python-утилиты;
- добавляет проверки;
- запускает backtest;
- сохраняет результаты;
- сообщает, если реализация выявила проблему в исследовательской гипотезе.

Если во время реализации возникает вопрос, меняющий экономический смысл стратегии, fill model, PnL или risk logic:
- не принимать скрытое решение в коде;
- сначала вынести вопрос в `RESEARCH.md`;
- явно зафиксировать принятое допущение.

## 8. Рабочий процесс

Для любой новой существенной задачи использовать следующий порядок.

### Шаг 1. Понять смысл

Сначала ответить:

- какой вопрос мы хотим проверить;
- зачем он нужен для market making;
- какое решение может измениться по результату.

### Шаг 2. Проверить данные

Если вопрос можно проверить на исходных данных — сначала анализ, потом изменение стратегии.

### Шаг 3. Обновить RESEARCH.md

Зафиксировать наблюдение, решение, допущение и следующий шаг.

### Шаг 4. Реализовать минимально достаточный код

Не строить заранее универсальную систему.

### Шаг 5. Проверить результат

Проверять не только «код работает», но и:

- результат экономически правдоподобен;
- нет look-ahead bias;
- нет двойного учета;
- fill model не слишком оптимистична;
- PnL сходится;
- inventory меняется ожидаемо;
- комиссии и funding применяются корректно.

### Шаг 6. Сохранить артефакты

Сохранять важные результаты так, чтобы к ним можно было вернуться:

- CSV;
- небольшие текстовые отчеты;
- графики;
- обновления `RESEARCH.md`.

## 9. Важные правила backtest

### Не использовать данные из будущего

Решение в момент `t` может использовать только информацию, известную к моменту `t`.

### Не считать touch равным fill автоматически

Если цена коснулась нашей лимитки, это еще не означает, что ордер был исполнен.

Модель fill должна быть явно описана.

### Не забывать очередь

При постановке лимитного ордера на уже существующий ценовой уровень перед нами может находиться объем других участников.

Точная очередь по L2 snapshot неизвестна, поэтому любое приближение должно быть явно зафиксировано.

### Не подгонять стратегию по трем дням

Три дня — очень маленькая выборка.

Не делать сильных выводов о долгосрочной прибыльности.

Не оптимизировать десятки коэффициентов ради красивого результата.

### Разделять источники PnL

По возможности отдельно считать:

- trading / spread PnL;
- inventory mark-to-market;
- fees;
- funding;
- итоговый net PnL.

### Помнить про gaps в данных

Если есть большой временной разрыв, нельзя бездумно считать, что старый ордер продолжал безопасно стоять все это время.

Примеры возможных параметров:

```text

hardInventoryLimit
quoteRefreshMs

queueModel
makerFeeBps
takerFeeBps
fundingWeight
imbalanceLevels

```

Не обязательно использовать все эти параметры.

Если параметр не нужен — не добавлять его.

У каждого параметра должен быть понятный смысл.

Избегать «магических» коэффициентов без объяснения.

## 11. Тестирование

Не нужно строить большой enterprise test suite.

Но критические части должны иметь проверки.

В первую очередь:

- изменение inventory после buy/sell fill;
- realized / unrealized PnL;
- комиссии;
- частичный fill;
- снятие ордера;
- fill только правильной стороной агрессора;
- hard inventory limit;
- отсутствие использования будущих событий;
- корректная обработка событий с одинаковым timestamp, если порядок важен.

Для сложных случаев предпочитать маленькие синтетические сценарии с очевидным ожидаемым результатом.

## 13. Финальный отчет

Финальный отчет должен быть короче и чище, чем `RESEARCH.md`.

В нем нужно показать:

1. что было сделано;
2. как устроена стратегия;
3. как устроена модель fills;
4. какие есть ключевые допущения;
5. результаты за 3 дня;
6. inventory / fill / risk metrics;
7. где стратегия зарабатывает и теряет;
8. ограничения результата;
9. что было бы следующим шагом при продолжении исследования.

Не выдавать тестовый backtest за доказательство production-прибыльности.

- стратегию;
- fills;
- очередь;
- latency;
- funding;
- комиссии;
- inventory;
- PnL;
- риск;
- интерпретацию результатов,

2. предложить простой вариант;
