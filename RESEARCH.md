# 2. Что известно о данных

## Order book

Доступны L2 snapshots глубиной 20 уровней:

- `datetime`
- `bid_price_1 ... bid_price_20`
- `ask_price_1 ... ask_price_20`
- `bid_qty_1 ... bid_qty_20`
- `ask_qty_1 ... ask_qty_20`

Предварительное наблюдение по 2026-03-19:

- около 1.43 млн snapshots за день;
- медианный интервал между snapshots около 52 мс;
- 99% интервалов меньше примерно 200 мс;
- встречаются редкие большие gaps;
- tick size выглядит равным 0.1 USD;
- spread почти всегда равен одному tick.

## Trades

Доступны:

- `datetime`
- `price`
- `size`
- `is_maker_ask`

Интерпретация из задания:

- `is_maker_ask = 1` — агрессор покупатель, исполнение произошло по ask;
- `is_maker_ask = 0` — агрессор продавец, исполнение произошло по bid.

Предварительное наблюдение по 2026-03-19:

- около 29 тыс. trade records;
- сделки идут неравномерно и часто группами;
- buy/sell aggressor распределены примерно симметрично.

## Funding

Доступны:

- `datetime`
- `funding_rate`

Funding обновляется примерно раз в 20 секунд.

Рабочая гипотеза: это поток текущего / прогнозного funding rate, а не событие фактического списания funding каждые 20 секунд.

## Готовый каркас backtest

- Три потока данных объединяются в один хронологический `List<Event>`.
- Используются `TradeEvent`, `OrderBookEvent` и `FundingRateEvent`.
- Trades заранее агрегируются по точному сочетанию
  `datetime + price + is_maker_ask`; funding сохраняется полностью.
- При одинаковом timestamp порядок фиксирован:
  `TradeEvent`, затем `OrderBookEvent`, затем `FundingRateEvent`.
- Дневной event tape сохраняется в Kryo-кэш. Повторная загрузка из Kryo по тестам
  примерно в пять раз быстрее чтения исходных Parquet.
- Backtest — обычный последовательный проход по событиям. В обработчики событий
  будет добавляться логика стратегии, fills, inventory, PnL и метрик.

# 6. Модель fills

Точная модель пока не зафиксирована.

Что уже известно:

- модель `market touched our price => full fill` слишком оптимистична;
- желательно использовать реальные trades;
- при постановке ордера на существующий уровень перед нами есть очередь;
- L2 snapshots не позволяют точно определить отмены ордеров впереди и позади нас.
- при одинаковом timestamp trade обрабатывается до snapshot стакана;
- в baseline стратегия пересчитывает котировки только после `BookSnapshotEvent`,
  поэтому созданный по snapshot ордер не может исполниться уже обработанным trade.

Рабочее направление:

- при постановке ордера оценивать объем очереди перед нами;
- уменьшать очередь реальным trade volume на нужной стороне;
- отдельно решить, как учитывать cancellations;
- явно описать консервативность / оптимистичность модели.

## Порядок обработки одного события

Для каждого входящего market event backtest выполняет три шага.

1. **Применить созревшие команды.** Команды place, cancel или изменения объема,
   отправленные ранее, меняют состояние наших bid/ask только после своей latency.
   До обработки market event применяются команды с `effectiveTime < eventTime`.
   Равенство времени трактуется консервативно: такая команда станет активной только
   после текущего события и не сможет исполниться им.
2. **Обработать текущее market event.** Только что пришедший trade или snapshot
   воздействует на уже активные ордера. Возможный частичный или полный fill меняет
   остаток ордера, cash, inventory, fees и realized PnL. Новый snapshot также меняет
   оценку unrealized PnL даже без fill. Одно market event учитывается для исполнения
   ровно один раз.
3. **Скорректировать желаемые bid/ask.** Стратегия видит уже обновленный рынок,
   fills и inventory, после чего решает, какие ордера хочет иметь. Активные ордера
   и уже отправленные, но еще не исполненные команды учитываются вместе, чтобы не
   создавать повторные place/cancel на каждом snapshot.

Для замены цены cancel старого и place нового ордера получают одинаковые время
отправки и latency. В момент исполнения сначала применяется cancel, затем place.
Это простое baseline-допущение исключает искусственное одновременное присутствие
старой и новой котировки, но может недооценивать реальный риск cancel/replace.

Изменение цены всегда моделируется как `cancel + place`. Правила изменения только
объема требуют отдельного решения: увеличение или уменьшение размера может по-разному
влиять на приоритет в очереди в зависимости от правил биржи.

## Учет отправленных команд

Стратегия не игнорирует place/cancel-команды, которые уже отправлены, но еще не
применены из-за latency. Для принятия решения используются четыре состояния:

1. **Фактическая позиция** — inventory после всех уже произошедших fills.
2. **Активные ордера** — bid/ask, которые сейчас реально могут исполниться.
3. **Проецируемое состояние ордеров** — результат последовательного применения всех
   уже отправленных команд к активным ордерам при условии, что новых fills не будет.
4. **Желаемое состояние ордеров** — bid/ask, которые стратегия хочет иметь после
   текущего market event.

После каждого события стратегия сравнивает желаемое состояние не только с активными
ордерами, а с проецируемым состоянием после всех команд в полете. Новая команда
создается только для оставшейся разницы. Поэтому уже отправленный place учитывается
и не дублируется на следующем snapshot.

Проецируемое состояние не считается будущей позицией: неизвестно, какие ордера
успеют исполниться. Для risk limits отдельно считается диапазон возможной позиции:

```text
minPosition = currentInventory - весь еще возможный sell volume
maxPosition = currentInventory + весь еще возможный buy volume
```

В этот объем входят активные ордера, ордера с отправленным cancel до момента его
применения и pending place, который еще может стать активным. Один и тот же ордер
учитывается только один раз. Новая команда не должна выводить этот диапазон за hard
inventory limits.

После неожиданного частичного или полного fill фактический inventory меняется,
стратегия заново определяет желаемые bid/ask и корректирует только разницу с уже
проецируемым состоянием. Команды в полете нельзя переписать задним числом: новая
корректирующая команда также проходит свою latency.

# 11. Допущения и ограничения

Текущий список:

1. Доступен L2 snapshot, а не L3/order-by-order data.

5. Fee schedule не задан.
6. Funding settlement mechanics не заданы.
7. Возможны gaps в рыночных данных.
8. Любая queue model будет приближением и должна быть явно описана.
9. Одинаковая latency для парных cancel/place — упрощение baseline; в реальности
   между снятием старого и появлением нового ордера возможны gap или overlap.

# 13. Отклоненные идеи / что уже не делаем

## Touch-fill как основная модель

Отклонено.

Причина: цена может коснуться нашего уровня, но перед нашим ордером может находиться значительный объем очереди.

## Группировка событий по timestamp во время replay

Отклонено на первом этапе.

Причина: отдельный вложенный цикл и обработка timestamp-пакетов не дают полезной
точности при отсутствии exchange sequence number. Для baseline достаточно плоского
потока с явным порядком типов событий и пересчетом котировок после snapshot стакана.

## 2026-09-24

**Решение:** каркас backtest реализован как последовательный replay единого
`List<Event>` за выбранные дни.

**Детали:** trades агрегируются по точному timestamp, цене и стороне; funding
сохраняется полностью; при одинаковом timestamp порядок равен
`TradeEvent -> OrderBookEvent -> FundingRateEvent`. Дневные tapes кэшируются через
Kryo, что примерно в пять раз ускоряет повторную загрузку по сравнению с Parquet.

**Причина:** исследователь может быстро менять стратегию и повторно прогонять три
дня, не меняя слой подготовки данных. Дальнейшие изменения backtest должны следовать
из зафиксированных решений по стратегии и модели исполнения.

---

## 2026-09-24

**Решение:** каждое market event обрабатывается в порядке
`созревшие команды -> fills и accounting -> новое решение по bid/ask`.

**Причина:** стратегия должна принимать новое решение по уже фактическому inventory,
а ордер не может исполниться событием, если его latency истекает ровно в timestamp
этого события. При изменении цены cancel выполняется перед связанным place.

---

## 2026-09-24

**Решение:** pending-команды обязательно учитываются при каждом новом решении.
Желаемые bid/ask сравниваются с проецируемым состоянием ордеров после всех уже
отправленных команд, а hard inventory limits проверяются по диапазону возможной
позиции.

**Причина:** это предотвращает дублирование команд и снижает риск перелета через
target inventory, но не подменяет неизвестные будущие fills искусственно рассчитанной
позицией.
