# Временные задачи на разработку baseline backtest

Этот файл — последовательный план реализации первого работающего варианта стратегии
S0. Задачи выполнять строго по порядку: каждая следующая опирается на результат
предыдущей.

После завершения всех четырех задач и переноса итоговых решений в `RESEARCH.md` файл
можно удалить.

## Общие правила выполнения

- Перед изменением экономической логики перечитать `TASK-ru.md`, `TASK-en.md`,
  `RESEARCH.md`, `FILL.md` и `METRICS.md`.
- Не менять принятый экономический смысл скрыто в коде. Новый спорный выбор сначала
  описать в `RESEARCH.md`.
- Основную реализацию писать на Java 21, без Spring и без универсального trading
  framework.
- Каждый метод с бизнес-логикой и каждый нетривиальный блок кратко комментировать
  по-русски.
- После каждой задачи запускать `gradlew.bat test` и не переходить дальше при
  падающих тестах.
- Сохранять простой последовательный порядок replay без look-ahead:
  созревшие команды -> fills -> обновление рынка -> решение стратегии ->
  reconciliation -> метрики.

# Задача 1. Завершить модель ордеров, очереди, fills и gaps

## Цель

Сделать так, чтобы лимитный ордер проходил полный реалистичный жизненный цикл:
от pending place через latency и очередь до partial/full fill, cancel или удаления
при gap.

## Что реализовать

1. Добавить в `Order` состояние очереди:
   - `queueAhead`;
   - признак или явное состояние инициализации очереди;
   - инициализацию только при фактической активации ордера;
   - уменьшение очереди подходящим trade volume;
   - корректное копирование состояния.
2. Изменить `OrderManager`:
   - смену цены и намеренное изменение размера выполнять через `cancel + place`;
   - убрать `RESIZE` из baseline;
   - сохранить новый `orderId` и новую очередь для replacement-ордера;
   - предоставить runner достаточно информации о только что активированных ордерах,
     чтобы назначить им очередь по последнему известному snapshot;
   - добавить явный reset active и pending orders для gap watchdog;
   - pending cancel не должен преждевременно исключать старый ордер из риска или fills.
3. Реализовать в `BacktestRunner` trade-based fill model строго по `FILL.md`:
   - buy исполняется только sell-aggressor trade по цене ордера или ниже;
   - sell исполняется только buy-aggressor trade по цене ордера или выше;
   - trade volume сначала расходует `queueAhead`;
   - остаток дает partial или full fill по цене нашего ордера;
   - один trade не может дать fill больше собственного объема;
   - snapshot сам по себе fill не создает.
4. Реализовать gap watchdog:
   - параметр `maxBookAgeNanos`, baseline — 1 секунда;
   - при переходе в stale-режим удалить active и pending orders и их очереди;
   - не обнулять inventory, portfolio и уже накопленные метрики;
   - не выставлять новые ордера без свежего snapshot;
   - первый snapshot после gap только восстанавливает рынок и разрешает новые place
     с обычной latency.

## Обязательные тесты

Покрыть синтетическими сценариями пункты раздела 13 `FILL.md`, в том числе:

- pending place и trade с timestamp, равным `effectiveTime`, не исполняются;
- очередь берется из правильного L2-уровня при активации;
- неправильная сторона и недошедшая цена не меняют очередь;
- trade сначала уменьшает очередь, затем дает partial/full fill;
- trade-through ограничен фактическим объемом trade;
- старый ордер может исполниться во время pending cancel;
- `cancel + place` не создает overlap и не переносит очередь;
- partial fill не вызывает автоматического пополнения;
- один `TradeEvent` учитывается один раз;
- gap reset удаляет ордера, но не торговое состояние.

## Критерий готовности

- Все правила `FILL.md` реализованы без использования будущих данных.
- Нет `RESIZE`, противоречащего принятой baseline-модели.
- Сумма partial fills не превышает исходный размер ордера.
- Все старые и новые тесты проходят.

# Задача 2. Реализовать portfolio accounting и проверить PnL

## Цель

Отделить учет позиции и PnL от replay-цикла и получить проверяемое разложение
финансового результата после каждого fill.

## Что реализовать

1. Создать небольшой класс `Portfolio` без лишних абстракций.
2. Хранить в нем:
   - текущий inventory;
   - average entry price;
   - realized PnL;
   - fees paid;
   - funding PnL, для S0 всегда `0`;
   - синтетический trading cash как независимую проверку accounting.
3. Реализовать применение fill:
   - fill в ту же сторону пересчитывает среднюю цену;
   - противоположный fill сначала закрывает позицию и создает realized PnL;
   - остаток после перехода через ноль открывает новую позицию по цене fill;
   - maker fee считается от notional и параметра `makerFeeBps`.
4. Реализовать расчет по последнему валидному mid:
   - unrealized PnL;
   - gross PnL;
   - net PnL;
   - net equity по контрольному cash ledger.
5. Заменить разрозненные поля `inventory`, `cash`, `feesPaid` в runner единым
   `Portfolio`.

## Обязательные тесты

- открытие long и short;
- добавление позиции в ту же сторону;
- частичное и полное закрытие;
- переход long -> short и short -> long;
- realized и unrealized PnL на простых ручных числах;
- положительная, нулевая и при необходимости отрицательная maker fee;
- после последовательности fills выполняется инвариант:

```text
realizedPnL + unrealizedPnL - feesPaid + fundingPnL
=
tradingCash + inventory * mid - feesPaid + fundingPnL
```

## Критерий готовности

- Accounting соответствует разделам 7–9 `RESEARCH.md` и `METRICS.md`.
- PnL не учитывается дважды.
- Все сценарии перехода позиции через ноль покрыты тестами.
- Все тесты проекта проходят.

# Задача 3. Реализовать и протестировать примитивную стратегию S0

## Цель

Получить первую намеренно простую стратегию, которую можно независимо тестировать и
запускать в том же backtest engine перед последовательным добавлением S1–S3.

## Что зафиксировать до кода

В `RESEARCH.md` явно записать baseline-значения и смысл параметров:

- `orderSize`;
- `hardInventoryLimit`;
- `orderLatencyNanos`;
- `maxBookAgeNanos`;
- `makerFeeBps`.

Не подбирать эти значения ради красивого PnL. Если данных недостаточно для точного
выбора, взять простой объяснимый baseline и отметить его как допущение.

Утвержденные baseline-значения:

```text
orderSize = 1.0 ETH
hardInventoryLimit = 5.0 ETH
orderLatencyNanos = 10_000_000       # 10 мс
maxBookAgeNanos = 1_000_000_000      # 1 секунда
makerFeeBps = 0.0
```

`orderSize` всегда используется целиком. S0 не уменьшает ордер до свободного остатка
hard limit. Если полный ордер `1.0 ETH` небезопасен, соответствующая сторона не
выставляется.

## Что реализовать

1. Собрать перечисленные параметры в одном видимом классе настроек.
2. Выделить минимальный контракт стратегии, позволяющий подменять S0 на S1/S2/S3,
   но не строить универсальный framework.
3. Реализовать S0:
   - bid на текущем best bid;
   - ask на текущем best ask;
   - одинаковый фиксированный размер;
   - без imbalance, trade flow и funding bias;
   - без котирования при отсутствующем или stale order book;
   - сторона, способная нарушить hard inventory limit с учетом active и pending
     ордеров, не выставляется;
   - после partial fill остаток ордера не пополняется автоматически.
4. Подключить S0 к `BacktestRunner` вместо текущего пустого
   `decideDesiredOrders()`.

### Точное правило hard inventory limit

Допустимый диапазон позиции — `[-5.0; +5.0] ETH` включительно. Для проверки стороны
используется worst-case позиция после всех еще возможных fills:

```text
новый bid допустим, если maxPosition + 1.0 <= +5.0
новый ask допустим, если minPosition - 1.0 >= -5.0
```

При этом:

- active orders, pending place и ордера с pending cancel входят в `PositionRange`;
- каждый `orderId` учитывается один раз;
- projected order, уже совпадающий с желаемым по стороне, цене и исходному размеру,
  сохраняется и не прибавляется к риску второй раз;
- partial fill не превращает остаток обратно в `1.0 ETH`;
- при `inventory = +5.0 ETH` новые bid запрещены, но ask разрешены;
- при `inventory = -5.0 ETH` новые ask запрещены, но bid разрешены.

### Replacement около hard limit

Смена best price требует нового order id и нового ордера полного размера `1.0 ETH`.
До завершения cancel старый ордер еще может исполниться, а затем может исполниться
новый. Поэтому при проверке replacement учитывается суммарный возможный результат
обоих fills.

Если одновременная отправка `cancel + place` может вывести позицию за hard limit:

1. отправить только cancel старого ордера;
2. не сохранять устаревшую котировку;
3. дождаться фактического применения cancel;
4. после освобождения risk capacity выставить новый ордер с обычной latency.

### Что намеренно отсутствует в S0

- уменьшенный размер ордера около лимита;
- soft inventory limit и inventory skew;
- taker risk-off или принудительное закрытие позиции;
- quote refresh timer;
- imbalance, trade flow и funding bias;
- искусственное закрытие позиции в конце дня.

## Обязательные тесты

- при свежем стакане создаются bid и ask на лучших ценах;
- при неизменном рынке не отправляются дублирующие команды;
- изменение best price вызывает `cancel + place`;
- без стакана и при stale book желаемые ордера пусты;
- опасная сторона отключается до нарушения hard limit;
- безопасная сторона около лимита остается доступной и может уменьшить inventory;
- active и pending orders учитываются в worst-case position range;
- стратегия не использует funding или будущие события.

## Критерий готовности

- S0 можно тестировать отдельно от загрузчика данных.
- Все существенные параметры находятся в одном месте и объяснены в `RESEARCH.md`.
- Hard limit нельзя нарушить полным исполнением всех еще возможных ордеров.
- Все тесты проекта проходят.

# Задача 4. Добавить baseline-метрики, почасовой timeline и полный запуск S0

## Цель

Замкнуть вертикальный срез `market events -> orders -> fills -> portfolio -> metrics`
и получить воспроизводимый результат S0 за три календарных дня.

## Что реализовать

1. Создать простой накопитель метрик по контракту `METRICS.md`:
   - realized, unrealized, gross и net PnL;
   - fees и funding PnL;
   - daily PnL;
   - final, max long, max short и средний абсолютный inventory по времени;
   - max drawdown по net equity;
   - activated orders, fill events, fully/partially filled orders;
   - buy/sell/total fill volume и average fill size;
   - cancel/replace count;
   - среднее время жизни активного ордера;
   - gap reset count и время без котирования из-за stale book.
2. Корректно завершать метрики в конце backtest:
   - использовать последний валидный mid;
   - закрыть время жизни оставшихся активных ордеров концом replay;
   - не закрывать inventory искусственной сделкой.
3. Создать простой универсальный накопитель почасовых срезов, например
   `HourlyStatisticsCollector`:
   - он не должен зависеть от конкретной стратегии;
   - runner вызывает его после обработки каждого market event;
   - накопитель сохраняет один срез на конец каждого часа UTC;
   - для среза используется последнее известное к этому моменту состояние, без
     интерполяции и без использования будущих событий;
   - три полных дня дают 72 компактные точки;
   - точные max drawdown и time-weighted inventory по-прежнему считаются по событиям,
     а не по часовым точкам.

   Минимальные поля почасового CSV:

```text
hourEndUtc
midPrice
inventory
realizedPnl
unrealizedPnl
grossPnl
feesPaid
fundingPnl
netPnl
fillsInHour
tradedVolumeInHour
gapResetsInHour
```

4. Сформировать результаты в отдельной папке класса стратегии:

```text
results/
└── SymmetricMarketMakingStrategy/
    ├── summary.csv
    ├── hourly.csv
    └── timeline.png
```

   Требования к отчетам:
   - `summary.csv` содержит строку на каждый день и строку `TOTAL`;
   - консольный отчет содержит те же основные итоги;
   - в консольном отчете и `summary.csv` обязательно указать имя класса стратегии и
     все основные условия запуска: `orderSize`, `hardInventoryLimit`,
     `orderLatencyNanos`/миллисекунды, `maxBookAgeNanos`/секунды и `makerFeeBps`;
   - по одному файлу должно быть понятно, при каких допущениях получен результат;
   - `timeline.png` — один компактный рисунок с 72 часовыми точками: динамика net PnL
     и inventory на двух простых панелях;
   - не строить сложную инфраструктуру отчетов или интерактивный dashboard.

5. Добавить автоматические проверки полного replay:
   - все итоговые числа конечны, без `NaN` и `Infinity`;
   - фактический inventory и worst-case position range не нарушают hard limit;
   - PnL-разложение сходится с контрольным cash ledger;
   - сумма daily PnL совпадает с total PnL;
   - при нарушении backtest завершается с понятной ошибкой.

6. Сразу выполнить один полный непрерывный replay всех трех дней, без отдельного
   короткого или ограниченного запуска:
   - сохранить `summary.csv`, `hourly.csv` и `timeline.png` в папке стратегии;
   - проверить правдоподобность количества orders, fills и gap resets;
   - кратко обновить наблюдения и следующий шаг в `RESEARCH.md`.

Отдельный синтетический end-to-end тест всей цепочки в этой задаче не добавлять.
Корректность итоговой интеграции проверяется полным replay реальных трех дней. Малые
unit-тесты отдельных расчетов метрик и часовых границ допустимы и нужны там, где
результат можно проверить вручную.

## Пока не добавлять

- inventory skew S1;
- imbalance или trade-flow filter S2;
- funding bias S3;
- taker risk-off;
- Sharpe, VaR, Expected Shortfall и набор сложных ratios;
- несколько markout-горизонтов;
- подбор параметров по этим трем дням;
- сложную инфраструктуру отчетов.

## Критерий готовности

- S0 воспроизводимо проходит все три дня одним непрерывным запуском.
- Дневные PnL складываются в общий PnL.
- Accounting-инвариант и hard inventory limit выполняются на полном replay.
- Результаты лежат в `results/SymmetricMarketMakingStrategy/`.
- Консольный отчет и `summary.csv` содержат минимальный набор из `METRICS.md`, имя
  стратегии и основные параметры запуска.
- `hourly.csv` содержит 72 почасовых среза без look-ahead, а `timeline.png` компактно
  показывает net PnL и inventory.
- `RESEARCH.md` содержит честные наблюдения по S0 и решение о следующем шаге S1.
